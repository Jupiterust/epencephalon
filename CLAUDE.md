# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`epencephalon` is the **cerebellum board of a robot project** — its job is inverse-kinematics solving. It runs on the **RoboMaster Development Board Type A** (STM32F427IIH6, Cortex-M4F, UFBGA176, 2 MB flash / 192 KB RAM / 64 KB CCMRAM).

Generated by STM32CubeMX 6.18.1 (FW_F4 V1.28.3) targeting the CMake toolchain, with **FreeRTOS (CMSIS-RTOS v2)** enabled. The intended direction is a **C++** application framework on top of FreeRTOS — note the build currently enables only `C` and `ASM`, so moving to C++ requires enabling `CXX` (see *Moving to C++* below). Developed in VS Code, under git.

Current state is a scaffold: `HAL_Init()` → `SystemClock_Config()` → `MX_GPIO_Init()` → `osKernelInitialize()` → `MX_FREERTOS_Init()` → `osKernelStart()`, with one empty `defaultTask` (512 B stack, `osPriorityNormal`) in `Core/Src/freertos.c`.

## Working rules for this repository

Each of these cost real time here once. They are ordered by how easily they fool you.

### The observation point is the object file, not the link product

The linker runs with `-Wl,--gc-sections`. Code that nothing references yet is **collected
away**, so `nm` on the `.elf` reporting zero symbols does **not** mean a source file failed
to compile or a library failed to integrate. Check `build/Debug/CMakeFiles/**/*.obj` instead
— note the extension is `.obj`, not `.o`. Once something calls into the code, the symbols
reappear in the `.elf`.

This turned a correct `can_master` integration into a false "it didn't link" for several
minutes.

### Validate the instrument on a short run before committing to a long one

Before any test that takes minutes, run the same harness with the durations turned down to
seconds. The 41-minute CAN soak was validated at 30 s + 90 s first, and that short run
exposed **four** harness bugs — absolute counters instead of deltas, a receive count that
was always zero because `poll()` had already drained the bus, a stray-reply criterion that
could never hold in loopback, and a period statistic that included the first sample of each
phase. Finding those after 41 minutes would have cost 41 minutes twice.

### Proving a binary changed: use content, not a hash taken too late

`shasum` before/after only works if the "before" is captured before **anything** that could
trigger a build. A `cmake --build … | grep error:` pipeline builds; taking the baseline after
it compares the new binary against itself and reports "unchanged". Prefer a content check
that answers the real question — is the new code in there:

```sh
strings build/Debug/epencephalon.bin | grep -c '^my_new_test_name$'
arm-none-eabi-nm -C build/Debug/epencephalon.elf | grep -c my_new_function
```

Also: `ninja: no work to do` after a piped build usually means the pipe already did it, not
that the build system is stale.

### Large buffers go in `.bss`, never on a task stack

`CanFrame rx[80]` is 1280 B; the app task had 2560 B. It faulted inside `PendSV_Handler` as
an unaligned `STM` during context save, which is the signature of a stack overflow.
`configCHECK_FOR_STACK_OVERFLOW` is now on (Option 2) with both hooks filled in
`freertos.c`'s USER CODE regions, so the next one names the task and blinks 0x55/0xAA on the
LEDs instead of producing a corrupt exception frame. Test code still reports
`uxTaskGetStackHighWaterMark` so stack sizes follow a measurement.

### When a test fails, suspect the expectation before the hardware

Three of the CAN failures were wrong expectations, not defects:

- **Arbitration**: the first frame queued onto an idle bus starts transmitting before the
  second is enqueued, so it cannot lose arbitration whatever its identifier. Only frames
  pending *together* are ranked. Fixed by queueing a blocker first.
- **Offline detection**: timing from "when the test stopped sending" instead of the library's
  own `lastSeenMs()` reported 32 ms against a 60 ms threshold. The reference point was wrong.
- **Clock stall**: spinning `poll()` to make `HAL_GetTick()` repeat 500 times cannot work
  when `poll()` is 3.6 µs and a tick is 1000 µs. The method was wrong, not the detector.

### Read the reference implementation before porting its data

The two fonts in the TFT reference driver use **different layouts** — 6x8 is column-major,
8x16 is row-major. Porting the first renderer and assuming the second matched produced a
garbled top line. The answer was in `TFTSPI_P8X16`, which had not been read.

### Use the right debugger tool for a fault

Hand-computing an exception frame from `MSP` produced nonsense twice (`lr = 0xa5a5a5a5`, the
FreeRTOS stack fill). One GDB `bt` named `PendSV_Handler` immediately. For any HardFault:
read `CFSR`/`HFSR`/`BFAR` first, then attach GDB for the backtrace — do not do stack
arithmetic by hand.

```sh
openocd -f openocd.cfg &                      # then, in gdb:
#   target extended-remote :3333 / monitor halt / bt
```

## VS Code workflow

Everything is wired up for **CMake Tools + Cortex-Debug**; no kit selection is needed because `CMakePresets.json` drives the toolchain.

- **Build**: `⇧⌘B` (task *编译 (Debug)*), or the CMake Tools status bar.
- **Flash without debugging**: task *烧录* (Terminal → Run Task). It builds first, then programs and resets.
- **Flash + debug**: `F5` → *调试 (DAP-Link)*. Builds, flashes, halts at `main`.
- **Attach to a running board**: *附加到运行中的板子* — no flash, no reset; for inspecting a hung/crashed target.

Equivalent commands outside the editor:

```sh
cmake --preset Debug                 # configure -> build/Debug/  (also: Release)
cmake --build --preset Debug         # -> epencephalon.elf / .hex / .bin / .map
openocd -f openocd.cfg -c "program build/Debug/epencephalon.elf verify reset exit"
```

Re-run the configure step after CubeMX adds or removes source files. If CMake's cache gets out of sync, use the task *重新配置 (删掉 build 重来)*.

There is no test suite and no lint config — a clean `-Wall` build is the only automated gate.

### Debug probe

`openocd.cfg` at the repo root is the **single** place probe settings live; both the flash task and the debug session source it. It is configured for **CMSIS-DAP / DAP-Link** over SWD at 4000 kHz.

- Switching probe = change the `interface/*.cfg` line (e.g. `interface/stlink.cfg`).
- `Could not initialize the debug port` or drops mid-flash → lower `adapter speed` to 1000.
- Board A's SWD header does **not** break out NRST, so `reset_config` is deliberately left at `stm32f4x.cfg`'s default (software reset via `sysresetreq`). Do not add `srst_only`.
- If the chip becomes unreachable (runaway code, read protection), run the *全片擦除* task. OpenOCD's F4 flash driver is named `stm32f2x`.

`.vscode/STM32F427.svd` (official ST, Apache-2.0) powers the peripheral-register viewer. FreeRTOS thread views come from the `mcu-debug.rtos-views` extension; `launch.json` deliberately does **not** set `"rtos": "FreeRTOS"`, because OpenOCD's RTOS awareness reads thread symbols that are not yet valid when halted at `main` and tends to hang the connection.

macOS note: `cortex-debug.gdbPath` / `openocdPath` in `.vscode/settings.json` are absolute because VS Code launched from the Dock does not inherit the shell `PATH`. Don't remove them.

## Generated-code contract

`epencephalon.ioc` is the source of truth for pin/clock/peripheral/FreeRTOS configuration. Regenerating from CubeMX **overwrites** `Core/Src/*.c`, `Core/Inc/*.h` (including `FreeRTOSConfig.h`), `startup_stm32f427xx.s`, `STM32F427xx_FLASH.ld`, and `cmake/stm32cubemx/CMakeLists.txt`.

- Only code between `/* USER CODE BEGIN X */` and `/* USER CODE END X */` survives regeneration. Never add code to a generated file outside those markers.
- **`FreeRTOSConfig.h` is generated** — change kernel options (heap size, hooks, tick rate) in CubeMX's FreeRTOS pane, not by hand.
- The **top-level `CMakeLists.txt` is generated once and never regenerated** — it is the intended home for hand-written sources, include paths, compile definitions and libraries. The `.hex`/`.bin` post-build rule lives there for that reason.
- Do not hand-edit `cmake/stm32cubemx/CMakeLists.txt`; change the `.ioc` instead.
- `.mxproject` is CubeMX's bookkeeping. Leave it alone.

**Adding a peripheral** (UART, SPI, TIM, CAN…) means editing the `.ioc` and regenerating — not just including a HAL header. The `.ioc` drives both the `HAL_*_MODULE_ENABLED` defines in `Core/Inc/stm32f4xx_hal_conf.h` and the driver `.c` files in `STM32_Drivers_Src`; a header included without both will fail to link. Currently enabled: GPIO, EXTI, DMA, RCC, FLASH, PWR, CORTEX.

## CMake structure

`cmake/stm32cubemx/CMakeLists.txt` defines three targets the executable consumes:

- `stm32cubemx` — INTERFACE library with all include dirs and the symbols `USE_HAL_DRIVER`, `STM32F427xx`, and `DEBUG` (Debug only).
- `STM32_Drivers` — OBJECT library of HAL/CMSIS sources plus `Core/Src/system_stm32f4xx.c`. This project compiles the **`Core/Src` copy**, not the CMSIS `Templates` copy that also exists under `Drivers/`.
- `FreeRTOS` — OBJECT library: kernel sources, `CMSIS_RTOS_V2/cmsis_os2.c`, `MemMang/heap_4.c`, `portable/GCC/ARM_CM4F/port.c`.

Two toolchain files exist. `cmake/gcc-arm-none-eabi.cmake` is what the presets use. `cmake/starm-clang.cmake` is an unused alternative (ST's clang) and is not installed here.

### Moving to C++

The toolchain file already carries C++ flags (`-fno-rtti -fno-exceptions -fno-threadsafe-statics`), but the project does not enable the language. To switch: add `CXX` to `enable_language()` and `project()` in the top-level `CMakeLists.txt`, then add `.cpp` sources via its `target_sources` block. Keep `main.c` and all CubeMX files as C and call into C++ across an `extern "C"` boundary — renaming generated files breaks regeneration. `-fno-exceptions` means `new` returns via the failure handler rather than throwing; on a 192 KB part, prefer static allocation over heap for IK working data.

## Application layer (C++)

Hand-written code lives in `App/`, which CubeMX never touches. The top-level `CMakeLists.txt` globs `App/**/*.cpp` into the build and enables `CXX`; everything CubeMX generates stays C. The boundary is `App/app_main.h` (`extern "C" void app_main(void)`), called from `StartDefaultTask` inside its USER CODE markers. **Never rename a generated `.c` to `.cpp`** — regeneration would recreate the `.c` and you would link two copies.

```
App/
  app_main.cpp        entry; creates the "app" task, then osThreadExit()s defaultTask
  drivers/oled_spi.*  SH1106 transport: HAL SPI1 + DMA2 + FreeRTOS semaphore
  drivers/oled.*      SH1106 driver (ported from the DJI RM_OLED C driver)
  drivers/led.*       8 LEDs on PG1..PG8
  drivers/key.*       PB2 user key, polled with debounce
  drivers/sdcard.*    SDIO + FATFS wrapper
  fonts/oledfont.h    6x12 ASCII + logo bitmaps
```

`app_main()` does **not** run the application in `defaultTask`. CubeMX gives that task a 512-byte stack, while `ffconf.h` sets `_FS_TINY 0`, so a single `FIL` carries a 512-byte sector buffer — it would overflow immediately. Instead `app_main()` spawns an "app" task with a 2560-byte stack and exits, so the stack size lives in C++ and survives regeneration.

### OLED notes carried over from the original driver

These were established on real hardware; do not "simplify" them away.

- The panel is **write-only and has no chip select** — CS is tied to GND on the module. SPI1 runs with software NSS; never drive a CS pin.
- SH1106 has 132 columns of RAM with the visible 128 centred, so column addresses need `kColOffset = 2`. The "set lower column address" command is `0x00-0x0F`, i.e. the **low** nibble — the original DJI code masked with `0xf0`, which silently discarded the offset and shifted the image 2 px left.
- `refresh()` compares each of the 8 pages against a copy of what the panel is showing and skips unchanged pages. A full push is 1024 bytes ≈ 2.9 ms at 2.8 MHz; a static screen costs zero SPI traffic.
- DC must stay stable for the whole byte it applies to, so `set_dc()` waits for SPI BSY before moving the line. A DMA completion interrupt means the DMA finished feeding the FIFO, **not** that the last byte left the shift register — `write_data()` therefore still spins on BSY afterwards.

## Clock tree

`SystemClock_Config()` in `Core/Src/main.c` runs the core at **180 MHz off the internal HSI**, not the external crystal:

HSI 16 MHz → PLLM 8 (2 MHz VCO in) → PLLN 180 (360 MHz) → PLLP /2 → **SYSCLK 180 MHz**, with `PWR_REGULATOR_VOLTAGE_SCALE1`, over-drive enabled, `FLASH_LATENCY_5`. AHB /1 = 180 MHz, APB1 /4 = 45 MHz, APB2 /2 = 90 MHz (APB timer clocks 90 / 180 MHz).

HSE and LSE pins are assigned in the `.ioc` but the clock tree does not use them.

> **`HSE_VALUE` is currently wrong for this board.** The `.ioc` carries CubeMX's F427 default of **25 MHz**, but RoboMaster Board A is fitted with a **12 MHz** crystal — confirmed against the official examples in `../DevelopmentBoard-Examples`, which all set `RCC.HSE_VALUE=12000000` (with PLLM 6 / PLLN 168 for 168 MHz). This is harmless today only because the PLL is fed from HSI. Anything that switches to HSE — USB, Ethernet, RTC, precise CAN/UART baud — must fix `HSE_VALUE` to 12000000 in CubeMX at the same time, or every clock-derived timing lands ~2x off.

Editing `SystemClock_Config()` by hand is reverted on the next generation; change the source in CubeMX and regenerate.

`SystemCoreClock` starts at 16000000 and is only corrected by `HAL_RCC_ClockConfig()`; don't read it before clock init. FreeRTOS takes `configCPU_CLOCK_HZ` from it at runtime.

## FreeRTOS

Tick 1000 Hz, `heap_4` with `configTOTAL_HEAP_SIZE` 15360 B, both static and dynamic allocation enabled. This FreeRTOS heap is **separate** from the newlib heap (`_Min_Heap_Size` 0x200 in the linker script); `osThreadNew`/`pvPortMalloc` draw from the former, `malloc`/`new` from the latter.

- **Interrupt priority ceiling**: `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` is 5. An ISR may call `...FromISR` APIs only if its NVIC preempt priority is **numerically ≥ 5**. ISRs at priority 0–4 preempt the kernel's critical sections and must never touch FreeRTOS. With priority group 4 (all 4 bits preemption, no sub-priority), this is the single most common source of hard-to-find crashes here.
- **HAL and FreeRTOS share SysTick.** CubeMX wired `SysTick_Handler()` to call `HAL_IncTick()` and then `xPortSysTickHandler()`. It works, but ST recommends giving HAL its own timebase (e.g. TIM6) when using an RTOS; if HAL timeouts start misbehaving, change the timebase in CubeMX's SYS pane.
- `HAL_Delay()` busy-waits and does not yield — inside a task use `osDelay()`. Calling either from an ISR deadlocks, since SysTick sits at priority 15 (lowest) and every peripheral ISR preempts it.
- `configCHECK_FOR_STACK_OVERFLOW` is **2 (Option 2)** and `configUSE_MALLOC_FAILED_HOOK` is
  **1**. Both hooks are implemented in `freertos.c`'s USER CODE regions and are deliberately
  stack-free — they record into `g_rtosFaultKind` / `g_rtosFaultTask` /
  `g_rtosHeapFreeAtFault` and then drive GPIOG directly (0x55/0xAA for a stack overflow,
  0x0F/0xF0 for a failed allocation). No printf, no allocation, no locks: the hook runs on a
  stack that is already damaged.
- FPU: `-mfloat-abi=hard` with the `ARM_CM4F` port, which lazily saves FPU context per task. IK math in tasks is fine; avoid float in ISRs unless you have verified the context save.

## SDIO / FATFS

CubeMX generates `FATFS/Target/sd_diskio.c` against the **DMA** BSP entry points (`BSP_SD_ReadBlocks_DMA`), regardless of whether SDIO DMA requests exist in the `.ioc`. If they don't, `hsd.hdmarx`/`hdmatx` are never linked and the first `f_mount` dereferences garbage — a precise bus fault with `BFAR = 0x20030000` (one byte past the end of RAM). `SdCard::mount()` guards against this and returns `last_error() == -2` instead.

**Where that guard has to sit matters.** `MX_SDIO_SD_Init()` only fills `hsd.Init`; it does **not** call `HAL_SD_Init()`. The real initialisation happens in `BSP_SD_Init()` (from `sd_diskio.c`'s `SD_initialize`, which also requires the scheduler to be running), and `__HAL_LINKDMA` runs inside the `HAL_SD_MspInit()` that `HAL_SD_Init()` triggers. So the DMA handles are NULL until `BSP_SD_Init()` has run — checking them before that always reports a false "no DMA". `SdCard::mount()` therefore calls `BSP_SD_Init()` itself first (which also switches the bus from 1-bit to 4-bit), then checks the handles, then mounts.

DMA2 stream assignment matters here. SPI1_TX, SDIO_RX and SDIO_TX are all offered on **DMA2_Stream3**, which is an XOR group — only one can own it. The conflict-free allocation is:

| Request | Stream | Channel |
|---|---|---|
| SPI1_TX | DMA2_Stream5 | 3 |
| SDIO_RX | DMA2_Stream3 | 4 |
| SDIO_TX | DMA2_Stream6 | 4 |

All three NVIC priorities must be **≥ 5** to stay below `configMAX_SYSCALL_INTERRUPT_PRIORITY`.

Verified working on hardware: FAT32, 8 KB clusters, ~14.5 GB card, and `boot.log` grows by 22 bytes per boot across power cycles.

FatFs is built with `_FS_REENTRANT 1` against the CMSIS-RTOS API and `_USE_LFN 0` (8.3 names only). SDIO's `sd_diskio` is blocking, so keep card I/O in a low-priority task, never in the IK path.

## CAN master (can_master)

`master/can_master` is a **symlink** into the joint-driver firmware repo's working tree
(`~/Documents/joint_motor/software/master/can_master`), and `external/joint_motor/{comm,core}`
are per-file symlinks to the two firmware headers it needs. There is physically one copy of
each on disk, so master and slave cannot drift apart — that is not enforced by a check, it is
impossible. Version pinning is git's job on the upstream side.

The dependency closure was derived with `-MMD`, not by reasoning: exactly `comm/can_ids.hpp`
and `core/flags.hpp`. **Linking the files rather than the directory is deliberate** — a third
upstream dependency must fail the build loudly instead of being picked up silently. For the
same reason the CMake source list is explicit and never globbed; that is also what keeps
`can_bus_loopback.*` (the host-test bus model, useless on the board) out of the build.

Two compile definitions are mandatory and **both fail silently if omitted**:

| macro | what happens without it |
|---|---|
| `JM_CAN_MASTER_PORT=JM_CAN_MASTER_PORT_FREERTOS` | `#error` (loud). It also binds `JM_CAN_MASTER_MIN_SAFE_IRQ_PRIORITY` to the scheduler threshold; picking `BAREMETAL` would make the NVIC check in `BxCanBus::start()` vacuous. |
| `JM_BXCAN_HAVE_HAL` | **Silent.** The whole driver is behind `#if defined(JM_BXCAN_HAVE_HAL)` (`can_bus_stm32_bxcan.cpp:13`, `.hpp:236`). Measured: 744 B object with **0 symbols** versus 6124 B with 37. Neither `README.md` nor `docs/CAN协议.md` documents it; only upstream's `check_bare_metal.sh` passes it. |

### Correctness preconditions this project is responsible for

From `docs/CAN协议.md` §0. All are silent when violated.

- All four CAN1 vectors at the **same** NVIC priority, **all four enabled**, each calling
  `onInterrupt()` after `HAL_CAN_IRQHandler`. `HAL_CAN_IRQHandler` does not know which vector
  entered it, so the receive path runs from all four. Configured in `can.c:125-132`; the glue
  is in `stm32f4xx_it.c`'s USER CODE regions.
- That priority ≥ `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` (5 here), or
  `taskENTER_CRITICAL()`'s BASEPRI mask does not cover them and the transmit ring's critical
  section becomes a no-op.
- CAN1's clock on even when only CAN2 is used: the 28 filter banks are physically CAN1's.
  The filter registers therefore read back from `CAN1->...` for **both** instances.
- Bit timing comes from `kTiming45MHz` (APB1 = 45 MHz → 1 Mbit/s, 86.67 % sample point). The
  driver overwrites whatever CubeMX put in `MX_CAN1_Init`, so the `.ioc` bit rate is
  irrelevant — but `MX_CAN1_Init` must still run, for MspInit's clock/GPIO/NVIC.

### Self-test (`App/can/`)

`runSelfTest()` runs to completion and prints one machine-readable line per case on UART7 at
921600 (same as the joint boards, so one log parser serves both). The report ring lives in
`.bss` and can be dumped with the debugger — that is how results are read here, since no
serial adapter is attached.

Measured on hardware, phase 0:

| | value | budget |
|---|---|---|
| CAN RX ISR (whole handler) | 8.2 µs avg, **14.8 µs max** | 165 µs drain budget |
| `CanMaster::poll()` | 3.6 µs avg, 7.5 µs max | 3 ms period |
| `Report::emit()` | ~38 µs | why printing is interval-based, never per-cycle |

**Known upstream gap, test kept red:** `T07a abort_ring_counted`. `cancel()`'s ring path
(`can_bus_stm32_bxcan.cpp:287-297`) only sets `withdrawn` and increments nothing, while the
mailbox path at `:303` increments `txAborted`. A request that times out while still queued
therefore lands on no counter, contradicting `can_bus.hpp:33-39` ("every control frame that
does not reach the wire lands on a counter"). The busier the ring, the likelier that path —
the evidence goes blind exactly when it is needed.

### Things that cost time here, so they are written down

- `BxCanBus` is `final` (`can_bus_stm32_bxcan.hpp:343`) — the clock cannot be stubbed by
  deriving from it. The stall test instead calls `HAL_SuspendTick()`, which works **only
  because the HAL time base is TIM6**, separate from FreeRTOS's SysTick. Spinning `poll()` to
  make `HAL_GetTick()` repeat 500 times cannot work: `poll()` is 3.6 µs, so only ~280 fit in
  a tick.
- `uwTick` is `extern __IO uint32_t` (`stm32f4xx_hal.h:204`) and `HAL_GetTick()` returns it
  unchanged, so the 32-bit wraparound run sets it to `0xFFFF0000` directly. Nothing is stubbed.
- In pure self-loopback every transmitted frame returns and is booked as a **stray reply**.
  That is the rig, not a defect: `strayReplies` cannot be zero. The criterion is
  `strayReplies == received` exactly. On a real bus it goes back to zero.
- `CanMaster::poll()` consumes frames from the bus, so a `receive()` loop after it always
  reads nothing. Count receptions from `stats().received`.
- Large test buffers belong in `.bss`. `CanFrame rx[80]` (1280 B) on the 2560 B app task
  stack faulted inside `PendSV_Handler` — an unaligned `STM` during context save, which is
  the signature of a stack overflow and is silent because `configCHECK_FOR_STACK_OVERFLOW`
  is off. The app stack is now 4096 B and the self-test reports
  `uxTaskGetStackHighWaterMark`.

## Memory and interrupts

- Linker regions: `FLASH` @ 0x08000000 (2 MB), `RAM` @ 0x20000000 (192 KB), `CCMRAM` @ 0x10000000 (64 KB). Current usage: ~16 KB flash, ~20 KB RAM (mostly the FreeRTOS heap in `.bss`).
- A `.ccmram` section exists (`__attribute__((section(".ccmram")))`), copied from flash at startup. CCMRAM is tightly coupled and ideal for IK scratch data, but **it is not reachable by DMA** — never place DMA buffers there.
- Vector table stays in flash; `USER_VECT_TAB_ADDRESS` is commented out in `system_stm32f4xx.c`.
- `Core/Src/stm32f4xx_it.c` holds the fault/system handlers. `SVC_Handler` and `PendSV_Handler` are **not** defined there — `FreeRTOSConfig.h` maps them to `vPortSVCHandler`/`xPortPendSVHandler` in `port.c`. Don't let CubeMX regenerate them into `stm32f4xx_it.c`, or the link will fail on duplicate symbols.
- `syscalls.c` / `sysmem.c` are newlib stubs linked against `--specs=nano.specs`; retargeting printf means implementing `_write` there, inside the USER CODE markers. Note `configUSE_NEWLIB_REENTRANT` is off, so newlib state is not per-task — avoid `printf` from multiple tasks without a mutex.
